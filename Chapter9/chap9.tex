	\paragraph{Scanning devices}\mbox{}\\
	The following code snippet demonstrates the implementation of a BLE scanning method used to detect nearby devices. The \textit{startScan} function initializes the scanning process by setting the \textit{scanState} to \textit{SCANNING} and resetting the list of discovered BLE devices. The scanning operation is performed using \textit{BleScanner}, with results processed by \textit{BleScanResultAggregator}. The detected devices are filtered to include only those with the name \textit{"THI-EKG"} and stored in a MutableState. 	This annotation ensures that the \textit{startScan} function is only executed on devices running Android API level \textbf{34 (Android 14, Upside Down Cake)} or higher. If the function is called on a lower API level, the compiler will issue a warning, and runtime execution may fail.  
	
	\textbf{\underline{@SuppressLint("MissingPermission")  }}\\
	This suppresses lint warnings related to missing Bluetooth permissions (such as \textit{BLUETOOTH\textunderscore SCAN} or \textit{ACCESS\textunderscore FINE\textunderscore LOCATION}). Normally, scanning for BLE devices requires specific permissions, and Android Studio would generate a warning if they are not explicitly checked. However, this annotation tells the lint tool to ignore such warnings, assuming the necessary permissions are already handled elsewhere in the code. Thus the permissions were always granted in the framwork of this thesis, these warning can be ignored, and will appear more often.

	private var scanJob: Job? = null
	
	@RequiresApi(Build.VERSION_CODES.UPSIDE_DOWN_CAKE)
	@SuppressLint("MissingPermission")
	private fun startScan(context: Context) {
		scanState.value = ScanState.SCANNING
		foundBLEDevices.value = mutableSetOf()
		
		val aggregator = BleScanResultAggregator()
		scanJob = BleScanner(context).scan()
		.map { aggregator.aggregateDevices(it) }
		.onEach {
			foundBLEDevices.value = it.stream()
			.filter { it.name == "THI-EKG" }
			.collect(Collectors.toSet())
		}
		.launchIn(viewModelScope)
		
		viewModelScope.launch {
			delay(2000)
			scanJob?.cancel()
			scanState.value = ScanState.DONE
		}
	}

\paragraph{Connect}\mbox{}\\
{\large 
	The provided BLE implementation is responsible for establishing a connection with a BLE-enabled device, receiving real-time data from specific BLE characteristics, and processing the incoming data to extract and analyze electrocardiographic (ECG) information. The functionality can be divided into the following key components:
	
	\underline{\textbf{1. BLE Connection Setup (Line 4-10)}}\mbox{}\\
	The function connect initializes the connection with a given BLE device. Using ClientBLEGatt.connect, a GATT connection is established, and the discovered services and characteristics are retrieved. The relevant characteristics include:
	
	\textit{signalCharacteristic:} Used for receiving real-time electrocardiographic data.\mbox{}\\
	\textit{appCommunicationCharacteristic:} Used for bidirectional communication with the BLE device.
	
	
	\underline{\textbf{2. Receiving and Processing Data from the Signal Characteristic}}\mbox{}\\
	The signalCharacteristic, continuously provides data in the form of a ByteArray. Each received data packet undergoes the following procedure:
	
	The received byte array is first converted into a list of integers. To enable concurrent processing, the data is then transmitted through a channel (channel.send(values) in line 15). A coroutine, executed by receiveData(viewModelScope), retrieves the streamed data from the channel and passes it to StoreWrapper.processDataList(datastream). (Since courotines and channels play a central role in this and other implementations, this chapter is followed by a brief introduction to these Kotlin-specific topics.)  The processed data is also added to the BPM.currList buffer for frequency analysis. Once the buffer exceeds 7500 samples, the QRS peak detection algorithm (Pan-Tompkins) is applied to identify heartbeats. 
	\\
	\mbox{}\\
	\underline{\textbf{3. Handling Application-Level BLE Communication}}\mbox{}\\
	During their bidirectional communication, both the microcontroller and the wirelessly connected device operate as senders and receivers.To ensure the correct operation, it is essential that the received data is accurately interpreted. This can be achieved by defining an Opcode for every desired behavior, which is contained in every sent packet. This allows incoming data packets to be classified based on their Opcode. As a result, each received packet can be assigned a meaning and subsequently processed accordingly.

		\label{fig:Packstructure with Opcode}
		\captionof{figure}{Packetstructure with Opcode (Source: Stefan Lindner)}
	\end{center} 
	
	 Furthermore the application can trigger actions in the microcontroller by sending a response packet. For example, it can start the recording mode. 
	
	\begin{center}
		\includegraphics[scale = 0.90]{/Users/eric/Downloads/GenericPacketEnglishResponse.drawio.png}

	Therfore each received notification undergoes:
	
	Validation using ResponseChecker.check.
	And packet reconstruction via PacketReassembler.reassemble, because some data is send fragmented by the microcontroller since the payload would be to large.Consquently the app needs to reassemble these packages to interpret them correctly.
	
	The check function aswell as the reassemble function will be explained in the following. 
	
	
	\underline{\textbf{4. Validating Packages (ResponseChecker)}}\mbox{}\\
	
	The check() function verifies whether a given packet corresponds to an expected response from the microcontroller. By verifying the expected Opcode.  The verification consists of multiple steps:
	
	\underline{1. Initial Length Check}\mbox{}\\
	If the byte array is too short ($\leq$ 2 bytes), it cannot be a valid response and is immediately discarded.  
	
	\underline{2. Packet Type Validation  }\mbox{}\\
	Calls `isResponsePacket(byteArray)`, a function that determines whether the received data is a response packet.  
	 If the data is not a response packet, the function exits early.  
	
	\underline{3. Opcode Verification }\mbox{}\\
	Calls `checkForExpectedOPCode(byteArray)`, which checks whether the response contains the expected operation code.  
	If the opcode does not match the expected one, the function exits early.  
	
	\underline{4. Cancelling the Timeout Mechanism }\mbox{}\\
	 If the response is valid, the current timeout timer (`currentTimer`) is canceled, ensuring that the system does not time out while waiting for the response.  
	
	\underline{5. Extracting and Processing the Response Message}\mbox{}\\
	The actual response message is extracted from the byte array starting at index 2. The message is decoded as a UTF-8 string.  
	
	\underline{6. Notifying the Listener}\mbox{}\\
	If a `responseReceivedListener` is set, it is triggered with the received byte array. The listener is likely responsible for further processing or handling the response.  
	
	\underline{7. Resetting the Expected Response }\mbox{}\\
	The variable `toCheck`, which presumably stores the expected response for comparison, is reset to `null`, indicating that the response-checking process has completed.  
	
	This function ensures that only valid and expected responses are processed in a BLE communication system. By implementing multiple validation checks (length, packet type, opcode), it prevents erroneous or irrelevant data from triggering unintended behavior.

	\underline{\textbf{5. Reassembling Packages (ResponseChecker)}}\mbox{}\\
	\\
	This function is responsible for reconstructing fragmented data packets. It ensures that data belonging to the same operation code (opcode) is sequentially assembled and processed once the transmission is complete.
	

	
	\underline{Initial Validation:}\mbox{}\\
	If the received byte array (data) is too short (less than 2 bytes), it is ignored as it is not a valid packet.
	\mbox{}\\
	\underline{Opcode Relevance Check:}\mbox{}\\
	The function checks if the opcode of the received packet is part of a predefined set of relevant opcodes (Constants.RELEVANT\textunderscore OPCODES).
	If the opcode is not relevant, the packet is ignored.
	\mbox{}\\
	\underline{Handling Unexpected Opcodes:}\mbox{}\\
	If a packet with a different opcode arrives while another one is still being processed (currentOpCode is not null), an exception is thrown. This prevents interleaved or mixed opcode sequences from corrupting the reassembly process.
	\mbox{}\\
	\underline{	Starting a New Message:}\mbox{}\\
	If no opcode is currently being processed (currentOpCode == null), the function assumes this packet marks the start of a new message and assigns its opcode to currentOpCode.
	\mbox{}\\
	\underline{Appending Data:}\mbox{}\\
	The function extracts the payload (excluding the first two bytes, which likely contain metadata such as the opcode) and appends it to the dataStr buffer.
	\mbox{}\\
	\underline{Completion Check \& Listener Notification:}\mbox{}\\
	If the packet indicates it is the last fragment (data.isLast()) and a listener (finishedListener) is set, the listener is notified with the assembled message.
	After notifying the listener, the function resets the dataStr buffer and currentOpCode to prepare for the next message.

	fun reassemble(data: ByteArray) {
		
		if(data.size < 2) {
			
			return
		}
		
		if(Constants.RELEVANT_OPCODES.contains(data.opCode()).not()){
			
			return
		}
		
		if(currentOpCode != null && this.currentOpCode != data.opCode()) {
			
			throw RuntimeException("Unexpected OpCode received!")
		}
		
		if(currentOpCode == null) {
			
			currentOpCode = data.opCode()
		}
		
		
		dataStr += String(data.sliceArray(2 until data.size), Charsets.UTF_8)
		
		if(data.isLast() && finishedListener != null){
			
			finishedListener!!(this.currentOpCode!!, this.dataStr)
			
			
			this.dataStr = ""
			this.currentOpCode = null
		}
	}

\subsection{Storewrapper}\mbox{}\\
The StoreWrapper class serves as a central component for processing and managing electrocardiographic (ECG) data in real-time. It is responsible for converting raw data received from the BLE signal characteristic into a format suitable for visualization. This transformation ensures that the incoming stream of ECG values can be efficiently rendered within the application’s graphical interface.
A key feature of the StoreWrapper class is its mapping functionality, which translates raw numerical values into drawable data points. This conversion is essential for accurately representing the ECG signal on-screen. Additionally, the class incorporates a ringbuffer, which provides an mechanism for storing and handling continuous data streams. The ringbuffer ensures that only the most recent samples are retained, enabling a sliding window approach for real-time signal visualization and processing.



\paragraph{Preparing ECG-Data}\mbox{}\\
{\large
	
	The provided code snippet is responsible for transforming raw electrocardiographic (EKG) data into a format suitable for visualization across different screen sizes. This transformation ensures that the signal is correctly scaled and displayed within the graphical interface, regardless of resolution or aspect ratio. The function achieves this with a time complexity of O(n), making it efficient for real-time applications.
	
	
	The function begins by initializing the shiftH parameter and preparing a mutable list (data) for storing processed values. If an external data source is provided, it is converted from a generic format into a list of Double values. Otherwise, an empty list is created.\mbox{}\\
	\mbox{}\\
	\underline{\textbf{Screen Size and Scaling Factors}}\mbox{}\\
	\mbox{}\\
	The width and height of the target display area are extracted from the size parameter. Additionally, the function determines the minimum (minV) and maximum (maxV) values within the buffer to establish the dynamic range of the data. If all values are equal, an artificial spread is introduced to prevent division by zero.\mbox{}\\
	\mbox{}\\
	\underline{\textbf{Normalization and Scaling}}\mbox{}\\
	\mbox{}\\
	The difference between maxV and minV (dv) is calculated to determine the range of data values. A step size (step) is then computed based on the available screen width and the buffer capacity, ensuring that data points are evenly distributed across the display. The coeff value is derived to scale the signal to fit within the available height while accounting for a vertical shift (shiftH).\mbox{}\\
	\mbox{}\\
	\underline{\textbf{Data Mapping for Graph Rendering}}\mbox{}\\
	\mbox{}\\
	A temporary list (dataTemp) holds the normalized data, which is then mapped to a new list (data). The mapping follows the formula:\mbox{}\\
	\mbox{}\\
	$data[i]=(maxV \text{-} dataTemp[i]) \times coeff+shiftH$ \mbox{}\\
	\mbox{}\\
	This equation ensures that the data is scaled appropriately for graphical representation.
	The function iterates over the dataset in a single pass (O(n) complexity), making it highly efficient for real-time applications. This guarantees smooth and responsive rendering, even with large data sets.

	\subsection{Calculating BPM (Pan-Tompkins Algorithm)}
	This code implements the Pan-Tompkins algorithm for detecting QRS complexes in an ECG signal. The algorithm processes the raw ECG data through multiple stages of filtering, differentiation, squaring, integration, and peak detection to identify heartbeats accurately.
	The panTompkins function in code 17 serves as the main processing pipeline. It first applies a bandpass filter, which is a combination of a low-pass and a high-pass filter, to remove noise and unwanted frequency components from the raw ECG data. The filtered signal then undergoes differentiation, enhancing the slope of the QRS complex.
	Next, the squared transformation is applied to amplify higher amplitude variations, making QRS peaks more distinguishable. The resulting signal is further processed using moving window integration, which smooths the waveform and highlights the QRS complexes by averaging values over a short period.
	Finally, peak detection is performed. A dynamic threshold is determined based on the signal’s overall amplitude, and only peaks that exceed this threshold and maintain a minimum interval (to prevent false detections) are identified as QRS complexes.
	The lowPassFilter and highPassFilter functions implement basic digital filters to isolate the frequency range of interest, while bandpassFilter applies them sequentially. The differentiate function enhances rapid signal changes characteristic of QRS complexes. The movingWindowIntegration function smooths the processed signal by averaging values over a predefined window.
	The detectPeaks function then scans the processed data for local maxima that exceed a threshold and are sufficiently spaced apart (at least 200 milliseconds), ensuring only valid QRS peaks are detected. The algorithm ultimately returns a list of QRS peak positions, which can be used for heart rate analysis and further ECG interpretation. \cite{pingale2014ecg}
		\begin{lstlisting}[label={fig:simpleSourceGen.cs}, caption={Pan-Tompkins algorithm}]
		 fun panTompkins(ecgData: List<Int>): List<Int> {
		
			val filteredData = bandpassFilter(ecgData)
			val derivativeData = differentiate(filteredData)
			val squaredData = derivativeData.map { it.toDouble().pow(2).toInt() }
			val integratedData = movingWindowIntegration(squaredData)
			return detectPeaks(integratedData, SAMPLE_RATE)
		}
		fun lowPassFilter(signal: List<Int>): List<Int> {
			var y = MutableList(signal.size) { 0 }
			for (n in signal.indices) {
				if (n >= 12) {
					y[n] = 2 * y[n - 1] - y[n - 2] + signal[n] - 2 * signal[n - 6] + signal[n - 12]
				} else {
					0 
				}
			}
			return y
		}
		
		fun highPassFilter(signal: List<Int>): List<Int> {
			var y = MutableList(signal.size) { 0 }
			for (n in signal.indices) {
				if (n >= 32) {
					y[n] = y[n - 1] - (signal[n] / 32) + signal[n - 16] - signal[n - 17] + (signal[n - 32] / 32)
				} else {
					0
				}
			}
			return y
		}
	
		fun bandpassFilter(ecgData: List<Int>): List<Int> {
			var lp_filtered = lowPassFilter(ecgData)
			var hp_filtered = highPassFilter(lp_filtered)
			return hp_filtered 
		}
	
		fun differentiate(data: List<Int>): List<Int> {
			var y = MutableList(data.size) { 0 }
			for (n in data.indices){
				if (n >= 4) {
					y[n] = (2 * data[n] + data[n - 1] - data[n - 3] - 2 * data[n - 4]) / 8
				}
				else{
					y[n] = 0
				}
			}
			return y
		}
		
		fun movingWindowIntegration(data: List<Int>): List<Int> {
			val result = mutableListOf<Int>()
			for (i in data.indices) {
				val start = maxOf(0, i - WINDOW_SIZE / 2)
				val end = minOf(data.size, i + WINDOW_SIZE / 2)
				val average = data.subList(start, end).average()
				result.add(average.toInt())
			}
			return result
		}
		
		
		fun detectPeaks(signal: List<Int>, fs: Int): List<Int> {
			val threshold = signal.sum() / signal.size 
			val peaks = mutableListOf<Int>()
			val rrInterval = (0.2 * fs).toInt()  
			var lastPeak = -rrInterval
			
			for (n in 1 until signal.size - 1) {
				if (signal[n] > threshold && signal[n] > signal[n - 1] && signal[n] > signal[n + 1]) {
					if (n - lastPeak >= rrInterval) {
						peaks.add(n)
						lastPeak = n
					}
				}
			}
			
			return peaks
		}

	\section{Summary}
	This thesis examined the design and implementation of a front-end application for real-time and long-term monitoring of electrocardiographic (ECG) data. The focus was on the processing of ECG-data, Bluetooth Low Energy (BLE) communication and the visualization of ECG curves in a mobile application. For this purpose, an application was developed in Jetpack Compose that continuously receives and processes ECG data and displays it in a user-friendly way.
	A key challenge  was the efficient processing of data streams that deliver new values every 8 milliseconds. This required optimized algorithms for storing, filtering and displaying the signals to ensure a smooth and delay-free visualization. In addition, mechanisms for recognizing response packets and reassembling fragmented data were implemented to ensure stable and reliable communication with the microcontroller.
	The developed application enables a reliable and intuitive visualization of ECG data in real time and thus provides a basis for further analysis and medical applications.

	\section{Outlook}
	The current implementation of the frontend application for real-time and 24-hour ECG monitoring provides a substantial foundation for visualizing and analyzing electrophysiological data. However, there remain several opportunities for improvement and further development that can enhance the application's usability, efficiency, and functionality.
	One key area for improvement is the user interface and user experience. A more intuitive and customizable UI can enhance user interaction, making it easier for both medical professionals and patients to navigate the application. Features such as customizable dashboards, improved accessibility, and better support for different screen sizes can significantly improve usability.
	Another important area is the integration of artificial intelligence to assist in anomaly detection. Machine learning models can be trained to recognize abnormal ECG patterns and provide early warnings about potential cardiac conditions. Implementing AI-based real-time classification and predictive analytics can enhance the system's capabilities and assist healthcare professionals in decision-making.
	The accuracy and efficiency of data processing can also be improved. Advanced filtering techniques can help reduce noise in the ECG signals, leading to more accurate readings. Optimizing data rendering and visualization can make the real-time display more fluid, especially when handling long-duration recordings.
	By addressing these areas, the application can evolve into a more robust and versatile tool, offering enhanced capabilities for medical professionals and patients alike. Future research should focus on improving usability, leveraging AI for anomaly detection, optimizing BLE communication, and ensuring compliance with medical standards.
